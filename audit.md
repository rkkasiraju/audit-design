Rule Audit History — Complete Understanding and Execution Plan

1. Objective

Implement audit history for the existing Rule Management module using:

* Angular for the UI.
* Spring Boot and Spring Data JPA for persistence.
* Microsoft SQL Server as the database.
* Existing table-level audit tables and triggers.
* A new rule-level audit history experience that presents changes meaningfully to users.

The primary goal is to preserve existing audit history, capture future changes reliably, and group multiple database changes into a single logical rule change without unnecessarily redesigning the current business tables.

2. Complete understanding of the rule design

A. Rule Details

The Rule Details section contains the metadata for one rule, such as:

* Rule ID
* Rule Name
* Alert Reason
* Alert Type
* Status
* Last Modified

Rule Details and Rule Conditions are separate UI sections, but both belong to the same rule.

B. Rule Conditions

Rule Conditions is a dynamic configuration containing an overall Match operator and an ordered list of top-level condition items.

The overall Match operator is either:

* All = AND
* Any = OR

Each top-level item is one of two types.

Overall Match

Applies to every top-level item in the rule.

Primary Single

One standalone condition directly under the rule.

Group ID = NULL

Multi-Group

A group containing multiple nested conditions.

Has its own inner Match operator.

Nested conditions

Each Multi-Group evaluates its nested conditions using its own All/Any operator.

The order of Primary Single and Multi-Group items is unrestricted. Users can add, edit, remove, and reorder conditions, change operators and values, and independently change the overall Match and each group’s inner Match.

For example, with an overall Match of All:

P_1 \land (C_1 \land C_2) \land P_2
\land P_3 \land (C_3 \lor C_4)

Here, are Primary Single conditions. The parenthesized expressions represent Multi-Groups, each with its own inner operator.

The audit implementation must preserve these logical relationships and, where relevant, the order of the conditions.

3. Current database structure

Based on the existing schema as described, there are three business tables.

Rule

One rule has many Rule Condition records.

Rule Condition

Linked to Rule by Rule ID. Stores standalone conditions and the records used to represent groups, according to the current schema.

Rule Condition Grouped

Stores nested conditions linked through Group ID.

The relationships are:

* Rule → Rule Condition: one-to-many, linked by Rule ID.
* Rule Condition → Rule Condition Grouped: one-to-many, linked by Group ID.
* A Primary Single condition has a null Group ID.
* A Multi-Group has its own representation and inner Match operator.

The exact columns used to represent group identity, group-level Match, and ordering should be verified against the actual schema before implementation.

4. Current audit mechanism and its limitation

The current implementation has audit tables and database triggers at the table level.

These triggers capture individual row operations, such as:

* Insert
* Update
* Delete

Depending on the existing audit schema, they may also capture the user, timestamp, and old/new values.

The limitation is that a single UI save can generate several independent database changes.

For example, one save might:

* Change the overall Match from All to Any.
* Update a Primary Single condition.
* Change a Multi-Group’s inner Match.
* Insert two grouped conditions.
* Delete one grouped condition.

The triggers can record these individual operations, but without a shared identifier or other reliable correlation mechanism, it is difficult to reconstruct that they all belong to one logical save.

The solution must preserve the low-level audit records while introducing a coherent rule-level history.

5. Recommended audit architecture

Use a hybrid approach with two levels of auditing.

Angular Rule Editor

User edits Rule Details or Rule Conditions

Spring Boot Rule Service

One transactional save operation

Generate Change ID · Identify authenticated user

SQL Server transaction

Set session context → Save all business entities

Existing triggers capture row-level changes

Technical audit

Existing audit tables extended with Change ID

Business audit

Logical change event and readable change details

Layer 1 — Technical audit

Keep the existing triggers and audit tables.

Extend the audit records with a ChangeId so records generated by the same logical save can be correlated across all three business tables.

Layer 2 — Business audit history

Introduce a rule-level audit event and its details. This layer explains what happened in business terms, such as:

* Rule created.
* Rule status changed.
* Overall Match changed.
* Primary Single condition updated.
* Multi-Group added or removed.
* Inner Match changed.
* Nested conditions added, modified, deleted, or reordered.

The technical audit provides evidence of individual row changes. The business audit provides the history users actually need to read.

Important: A Change ID alone does not create a business audit summary. The application must either calculate the changes by comparing the old and new rule structures or record explicit domain-level change events.

6. Proposed audit data model

A. Rule Audit Header

One record represents one logical rule change.

Column	Purpose
AuditId	Unique audit event identifier
ChangeId	Correlation ID shared by related database changes
RuleId	Rule being changed
Action	Created, Updated, Activated, Deactivated, Deleted
ChangedBy	Authenticated application user
ChangedAt	Audit timestamp
Comments	Optional user comment

B. Rule Audit Detail

One or more detail records describe the changes in that event.

Column	Purpose
AuditDetailId	Unique detail identifier
AuditId	Parent audit event
EntityType	Rule, Primary Single, Multi-Group, Grouped Condition
EntityId	Identifier of the affected entity, where available
Operation	Insert, Update, Delete, Reorder
FieldName	Changed field
OldValue	Previous value
NewValue	New value

The technical audit tables remain separate and continue recording the database changes. The new business audit tables provide the history view and can reference the same Change ID.

You may be able to simplify this model if your existing audit tables already contain enough information. Inspect them before adding duplicate storage.

7. SQL Server implementation with Spring Data JPA

The intended implementation is to use Spring’s @Transactional and SQL Server’s SESSION_CONTEXT.

Step 1 — Add Change ID to existing audit tables

If your audit tables do not already have a suitable correlation column, add a nullable UNIQUEIDENTIFIER column to them.

For example:

ALTER TABLE dbo.Rule_Audit
ADD ChangeId UNIQUEIDENTIFIER NULL;

Repeat for the audit tables associated with Rule Condition and Rule Condition Grouped, using their actual names.

Existing audit rows remain valid with NULL. Do not fabricate Change IDs for historical records that cannot be reliably correlated.

You do not need to add Change ID columns to the three business tables just for audit correlation.

Step 2 — Establish the audit context in Spring

Generate one Change ID for the entire logical save.

UUID changeId = UUID.randomUUID();

Set the context on the same SQL Server connection used for the business writes:

EXEC sys.sp_set_session_context
    @key = N'ChangeId',
    @value = @ChangeId;

In Spring, use transaction-aware JDBC access, such as JdbcTemplate, sharing the same DataSource and transaction manager as JPA. A connection callback can execute the procedure using a CallableStatement.

Do not assume that a separate repository call or a newly acquired connection will inherit the context.

Step 3 — Modify the existing triggers

Each trigger reads the context:

DECLARE @ChangeId UNIQUEIDENTIFIER =
    TRY_CONVERT(
        UNIQUEIDENTIFIER,
        SESSION_CONTEXT(N'ChangeId')
    );

The trigger inserts the Change ID into its audit table alongside the existing audit data.

Triggers must handle multi-row operations correctly. They should not assume that one SQL statement changes only one row.

Step 4 — Save all entities in one transaction

The service should:

* Begin the transaction.
* Establish the Change ID and authenticated user context.
* Load the current rule and condition structure.
* Compare the old and submitted structures.
* Save Rule, Rule Condition, and Rule Condition Grouped changes.
* Flush pending JPA changes while the context is active.
* Save the business audit header and details.
* Commit the transaction.
* Clear the session context safely before the connection is reused.

On failure, roll back the transaction and ensure cleanup runs without masking the original exception.

SQL Server session context is session-scoped, not transaction-scoped. Therefore, cleanup is important when using pooled connections. Avoid read-only session context settings if the value must subsequently be cleared.

The audit records and business changes should commit atomically when they are part of the same database transaction.

8. Preserve historical audit records in production

The new architecture applies to future changes, but existing production rules need a separate migration plan.

Historical data strategy

Existing audit records contain sufficient detail

Reconstruct and correlate historical changes where possible. Backfill the new business audit structure and preserve links to the original audit records.

Existing audit records are incomplete

Display only what can be verified. Mark reconstructed entries as historical and avoid inventing missing values, identities, or timestamps.

No usable history exists

Create a baseline snapshot of the current rule configuration, clearly labeled with the migration timestamp. Do not represent this snapshot as the original creation event.

Migration sequence

* Inspect the existing audit tables, triggers, retention policies, and captured columns.
* Back up the relevant production data.
* Build and test a backfill process against a production-like database.
* Reconstruct historical events where evidence allows.
* Validate the results against the existing audit records and current business tables.
* Deploy the new auditing mechanism with a controlled cutover.
* Monitor for missing, duplicate, or uncorrelated events.

Make the backfill idempotent so that rerunning it does not create duplicate history.

10. Complete execution plan

I would implement this in the following order.

* Inspect the current implementation. Review the three business tables, their primary and foreign keys, ordering fields, group Match storage, existing audit tables, and triggers.
* Finalize the audit data model. Decide whether the existing audit tables can be extended or whether separate Rule Audit Header and Detail tables are required.
* Implement Change ID propagation. Add transaction-aware SQL Server session context handling in Spring, ensuring JPA and JDBC share the same transaction and connection.
* Update existing triggers. Capture the Change ID and retain the existing audit fields and old/new values.
* Implement business-level change detection. Compare the previous and submitted rule structures using stable identifiers. Detect field updates, additions, deletions, Match changes, and reordering.
* Implement atomic persistence. Save the business entities and required audit records in the same transaction.
* Backfill historical data. Convert recoverable existing trigger records into the new history model and establish clearly labeled baselines where necessary.
* Build the audit API and Angular drawer. Reuse the existing Ghost Card Exclusion pattern and display grouped rule changes.
* Test and deploy incrementally. Validate rollback behavior, pooled connection cleanup, multi-row triggers, nested condition changes, concurrent edits, migration idempotency, and audit completeness.

11. Acceptance criteria

The implementation is complete when:

* Every supported rule modification is audited.
* A single save operation produces a coherent logical history event.
* Related trigger records can be correlated using the Change ID.
* Old and new values are available for applicable changes.
* Primary Single and nested conditions retain their correct group relationships.
* Existing audit records remain preserved.
* Audit writes fail safely with the business transaction when auditing is mandatory.
* Reused database connections cannot leak audit context between requests.
* Users can inspect the history from the rule details screen without modifying audit records.

Final recommendation: Do not start by changing all your JPA entities or adding columns to business tables. First inspect the current SQL Server audit schema and transaction boundaries. Then implement Change ID propagation, extend the triggers, add business-level change detection, and build the historical backfill. This approach minimizes changes to the existing rule engine while providing a reliable audit trail.
